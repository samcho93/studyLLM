❓ 4비트가 8비트보다 큰 이유는?

허브의 실제 파일 크기다. 답: q4는 행렬곱 가중치만 4비트, 임베딩 표(Gather)는 fp32로 둔다. SmolLM2 임베딩 28.3M × 4B = 113MB, 나머지 106M × 0.5B ≈ 53MB + 묶음 scale ≈ 182MB. Qwen은 임베딩만 545MB.

2주차 “어휘 크기 ↔ 토큰 수” 맞바꿈의 또 다른 비용: 어휘가 크면 임베딩 표가 커진다.

8비트 대칭 양자화

scale = max(|w|) / 127
q     = round(w / scale)      # −127…127, 1바이트
ŵ     = q × scale             # 오차 ≤ scale / 2
가중치 4,096개scaleRMSE0이 된 비율
정상 (σ = 0.02)0.000570.000171.1%
이상치 8.0 하나0.0630.0169 (100배)87.9%

C2 실행 결과다. 이상치 하나가 scale을 키워 나머지 값의 88%가 0으로 뭉개진다. 실제 LLM에도 이런 이상치 채널이 있어서, 묶음(group) 양자화나 이상치를 따로 두는 기법(LLM.int8 등)이 나왔다고 짚는다.

데모 · 온디바이스 LLM 실행기

시연 순서

  1. 녹화된 결과부터 보여 준다(아직 아무것도 받지 않았다)
  2. SmolLM2 불러오기 → 캐시되어 있으면 수 초
  3. 영어 질문 → 그럴듯한 한 문장. 한국어 질문 → 질문을 되풀이하는 엉뚱한 답
  4. “우리 학과 사실” → GPU 수 때문이라며 지어낸다(환각). “문서를 넣어 주면” → “문서에 없다”면서 동시에 “최대 12시간”이라고 말하는 모순 → 근거 + 모델 크기 둘 다 필요
  5. 개발자 도구 네트워크 탭 → 생성 중 요청 0개. 와이파이를 끄고 한 번 더
  6. (캐시해 두었다면) Qwen2.5-0.5B: 한국어는 되지만 약 2 tok/s. “우리 학과 사실”에는 “정보가 없다”고 답하고(지시 미세조정의 효과), “문서를 넣어 주면”에서는 오히려 문서를 무시하고 일반론을 편다 → 크다고 근거를 잘 쓰는 것은 아니다. 수업 PC 기준 캐시에서 불러오는 데만 약 63초

속도를 재는 두 숫자

  • 첫 토큰 지연 (TTFT): 프롬프트 전체 처리(prefill) → 프롬프트가 길수록 길다
  • 초당 토큰 (tok/s): 한 토큰마다 가중치 전체를 한 번 읽는다 → 대역폭 ÷ 모델 바이트
  • 한국어는 영어 중심 어휘에서 토큰이 몇 배 → 같은 답도 몇 배 느리다

관찰 5: Qwen은 SmolLM2보다 약 3.7배 크다. tok/s 비가 비슷한지 표로 확인시킨다. 다른 탭·백그라운드 작업이 많으면 숫자가 크게 흔들린다는 점도 경험하게 한다(측정 조건 통제).

부록 B · C1 정답

const models = {
  'SmolLM2-135M': { D: 576, layers: 30, vocab: 49152, ffn: 1536, heads: 9, kvHeads: 3, qkvBias: false },
  'Qwen2.5-0.5B': { D: 896, layers: 24, vocab: 151936, ffn: 4864, heads: 14, kvHeads: 2, qkvBias: true },
};
function countParams(c) {
  const headDim = c.D / c.heads;
  const kvDim = c.kvHeads * headDim;
  const embedding = c.vocab * c.D;
  let perLayer = c.D * c.D + 2 * c.D * kvDim + c.D * c.D;
  if (c.qkvBias) perLayer += c.D + 2 * kvDim;
  perLayer += 3 * c.D * c.ffn + 2 * c.D;
  return { embedding, perLayer, total: embedding + perLayer * c.layers + c.D };
}
const BYTES = { fp32: 4, fp16: 2, int8: 1, int4: 0.5 };
console.table(Object.entries(models).map(([name, c]) => {
  const p = countParams(c);
  const row = { name, totalM: +(p.total / 1e6).toFixed(1), embShare: +(p.embedding / p.total).toFixed(3) };
  for (const [k, b] of Object.entries(BYTES)) row[k + 'MB'] = Math.round((p.total * b) / 1e6);
  return row;
}));

실행 결과: SmolLM2 134.5M · 임베딩 21% · fp32 538 / fp16 269 / int8 135 / int4 67MB. Qwen 494.0M · 27.6% · 1,976 / 988 / 494 / 247MB.

허브 파일과 비교: int8은 거의 같고(137 · 512), int4 계산값(67 · 247)과 실제 q4(182 · 786)는 크게 다르다 → 임베딩 fp32와 묶음 scale 때문. 이 차이를 설명하는 것이 C1의 진짜 목표다.

부록 B · C2 · C3 정답

import { mulberry32, gaussian } from '/assets/js/core/rng.js';
const rand = mulberry32(16);
const w = Float32Array.from({ length: 4096 }, () => gaussian(rand) * 0.02);
// C2
function quantizeInt8(w) {
  let m = 0;
  for (const x of w) m = Math.max(m, Math.abs(x));
  const scale = m / 127;
  return { q: Int8Array.from(w, (x) => Math.round(x / scale)), scale };
}
const dequantize = ({ q, scale }) => Float32Array.from(q, (v) => v * scale);
function report(name, w) {
  const qw = quantizeInt8(w), back = dequantize(qw);
  let maxErr = 0, sq = 0;
  for (let i = 0; i < w.length; i++) { const e = Math.abs(w[i] - back[i]); maxErr = Math.max(maxErr, e); sq += e * e; }
  return { name, scale: qw.scale, maxErr, rmse: Math.sqrt(sq / w.length), distinct: new Set(qw.q).size, zeroFrac: qw.q.filter((v) => v === 0).length / w.length };
}
const wo = Float32Array.from(w); wo[7] = 8.0;
console.table([report('정상', w), report('이상치 1개', wo)]);
// C3
function groupQuantRmse(w, groupSize, bits) {
  const qmax = 2 ** (bits - 1) - 1;
  let sq = 0;
  for (let g = 0; g < w.length; g += groupSize) {
    const group = w.subarray(g, g + groupSize);
    let m = 0;
    for (const x of group) m = Math.max(m, Math.abs(x));
    const scale = m / qmax || 1;
    for (const x of group) { const e = x - Math.round(x / scale) * scale; sq += e * e; }
  }
  return Math.sqrt(sq / w.length);
}
const rows = [];
for (const bits of [8, 4]) for (const groupSize of [32, 128, 1024, 4096])
  rows.push({ bits, groupSize, rmse: groupQuantRmse(wo, groupSize, bits), bitsPerWeight: +(bits + 32 / groupSize).toFixed(3) });
console.table(rows);

C2: 정상 scale 0.000574 · RMSE 0.000167 · 서로 다른 값 205개 · 0 비율 1.1% / 이상치 scale 0.0630 · RMSE 0.0169 · 서로 다른 값 4개 · 0 비율 87.9%.

C3 (이상치 포함): 8비트 묶음 32 → RMSE 1.50e-3 (9비트/가중치), 128 → 3.00e-3, 1024 → 8.37e-3, 4096 → 1.69e-2. 4비트 묶음 32 → 2.48e-3 (5비트), 4096 → 2.03e-2. 4비트 + 작은 묶음(2.48e-3)이 8비트 + 큰 묶음(1.69e-2)보다 7배 정확하다. 실제 q4 형식이 묶음 32를 쓰는 이유.

부록 B · C4 정답

const PRICE = { inPer1M: 1.0, outPer1M: 5.0 };
const scenario = { students: 30, questionsPerWeek: 20, weeks: 16, inTokens: 600, outTokens: 150 };
const LOCAL_MB = { 'SmolLM2-135M': 137, 'Qwen2.5-0.5B': 512 };
function apiCost(s) {
  const n = s.students * s.questionsPerWeek * s.weeks;
  return (n * (s.inTokens * PRICE.inPer1M + s.outTokens * PRICE.outPer1M)) / 1e6;
}
const localDownloadGB = (s, model) => (s.students * LOCAL_MB[model]) / 1000;
function choose({ hasPersonalData, needsKorean, offline }) {
  if (hasPersonalData || offline) return needsKorean ? '로컬 Qwen2.5-0.5B (또는 사내 서버의 더 큰 모델)' : '로컬 SmolLM2-135M';
  return needsKorean ? 'API (한국어 품질)' : 'API 또는 로컬 — 비용 비교로 결정';
}
console.table([{ api달러: apiCost(scenario), smolGB: localDownloadGB(scenario, 'SmolLM2-135M'), qwenGB: localDownloadGB(scenario, 'Qwen2.5-0.5B') }]);
console.log(choose({ hasPersonalData: true, needsKorean: true, offline: false }));
console.log(choose({ hasPersonalData: false, needsKorean: true, offline: false }));

실행 결과: 9,600문항 → 12.96달러 · SmolLM2 4.11GB · Qwen 15.36GB. 판단: 개인정보+한국어 → 로컬 Qwen(또는 사내 서버), 그 외 한국어 → API.

정답이 하나가 아니다. 규칙의 근거(개인정보 우선, 품질 요구)를 설명하면 인정한다. “0.5B로는 한국어 상담 품질이 부족하다 → 사내 GPU 서버에 더 큰 모델”이라는 답은 우수로 본다.

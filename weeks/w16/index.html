내 컴퓨터 안의 LLM

지금까지 실제 LLM은 API 너머 남의 서버에서 돌았다. 질문은 인터넷을 건너가고, 토큰마다 돈을 냈다. 이번 주는 진짜 사전학습·지시 미세조정된 LLM을 이 브라우저 탭 안에서 돌린다. 서버도 키도 없다. 대신 무엇을 포기하는지 숫자로 잰다.

2왜 필요한가

11주차 API 플레이그라운드에서 “보내기”를 누르면 질문 전체가 공급자의 서버로 간다. 학생 상담 기록, 환자 정보, 회사 설계 문서처럼 밖으로 나가면 안 되는 글이라면 이것 자체가 문제다. 게다가 요청마다 토큰 요금이 붙고, 네트워크가 끊기거나 학교 방화벽이 API 주소를 막으면 아무것도 할 수 없다.

그렇다면 모델을 내 기기에서 돌리면 된다. 7주차에 미니 GPT를 브라우저에서 학습시켰듯, 이미 학습된 LLM도 브라우저에서 추론할 수 있다. 문제는 크기다. 우리 미니 GPT는 파라미터 약 10만 개였고, 쓸 만한 챗봇은 수억~수천억 개다. 이번 주의 질문은 이것이다. 얼마나 작아야 내려받을 수 있고, 그만큼 작으면 얼마나 멍청해지는가?

3개념

브라우저에서 LLM이 도는 구조

모델은 ONNX라는 공통 형식으로 저장되어 있고, ONNX Runtime Web이 이를 WebAssembly(WASM)로 계산한다. 그래픽카드를 쓰는 WebGPU도 있지만 지원 여부가 기기마다 달라서 이번 주는 모든 PC에서 동작하는 WASM으로 고정한다.

모델 크기 = 파라미터 수 × 가중치 한 개의 바이트

같은 파라미터를 몇 비트로 저장하느냐가 양자화(quantization)다. 허브에 실제로 올라와 있는 ONNX 파일 크기는 이렇다.

저장 형식가중치당SmolLM2-135MQwen2.5-0.5B
fp32 (원본 학습 정밀도)4바이트540MB1,994MB
fp162바이트270MB997MB

q4f16 (4비트, 나머지 fp16)0.5바이트 + α118MB483MB

이상한 줄이 하나 있다. 4비트(q4)가 8비트(int8)보다 크다. q4 파일은 행렬곱 가중치만 4비트로 줄이고 임베딩 표는 fp32(4바이트)로 둔다. SmolLM2의 임베딩 표 2,830만 개 × 4바이트 = 113MB가 파일의 절반 이상을 차지한다. Qwen은 어휘가 15만 개라 임베딩만 545MB다. 어휘가 큰 다국어 모델일수록 “임베딩 표를 어떻게 저장하느냐”가 크기를 좌우한다. 2주차의 어휘 크기 대 토큰 수 맞바꿈이 여기서 다시 나온다.

양자화는 어떻게 하나: 8비트 대칭 양자화

scale = max(|w|) / 127          # 한 묶음(행 또는 32개)마다 하나
q     = round(w / scale)        # −127 … 127 정수, 1바이트
ŵ     = q × scale               # 계산할 때 되돌린다 → 오차 |w − ŵ| ≤ scale / 2

값의 범위를 256칸으로 나누어 가장 가까운 칸 번호만 저장한다. 묶음 안에 튀는 값(이상치) 하나가 있으면 scale이 커져 나머지 값들이 모두 거칠게 표현된다. 그래서 묶음을 작게(예: 32개) 나눌수록 정확하지만 scale을 저장할 공간이 는다. Challenge C2~C3에서 직접 확인한다.

속도: 첫 토큰 지연과 초당 토큰 수

  • 첫 토큰 지연(TTFT): 프롬프트 전체를 한 번에 처리(prefill)하고 첫 토큰이 나오기까지. 프롬프트가 길수록 길어진다.
  • 초당 토큰 수(tok/s): 그 뒤로 토큰을 하나씩 만드는 속도(decode). 토큰 하나를 만들 때마다 가중치 전체를 메모리에서 한 번 읽어야 하므로, 대략 메모리 대역폭 ÷ 모델 바이트에 묶인다. 모델이 4배 크면 대략 4배 느리다.

한국어는 여기서 한 번 더 손해를 본다. 영어 중심 어휘(SmolLM2)는 한국어를 바이트 조각으로 잘게 쪼개므로 같은 뜻의 답에 토큰이 몇 배 더 든다. 2주차와 studyRAG 1주차 토큰 카운터에서 본 현상이 이제 속도로 나타난다.

C1. 모델 크기 어림하기★

Llama 계열 모델의 설정값으로 파라미터 수를 세는 함수를 완성한다. 층 하나에는 어텐션(q · k · v · o)과 MLP(gate · up · down 세 행렬), 정규화 두 개가 있다. k와 v는 헤드를 공유(GQA)하므로 크기가 D × (kvHeads × headDim)이다. 두 모델 모두 134.5M과 494.0M에 가깝게 나와야 한다(Qwen은 q · k · v에 편향이 있다). 그다음 저장 형식별 크기(MB)를 표로 만든다.

C2. 8비트 양자화 직접 하기★★

가중치 배열을 int8로 양자화하고 되돌렸을 때의 오차를 잰다. 정규분포 가중치 4,096개로 시작한 뒤, 값 하나를 이상치(8.0)로 바꿔 오차가 어떻게 변하는지 본다.

function report(name, w) {
  const qw = quantizeInt8(w);
  const back = dequantize(qw);
  let maxErr = 0, sq = 0;
  for (let i = 0; i < w.length; i++) {
    const e = Math.abs(w[i] - back[i]);
    maxErr = Math.max(maxErr, e);

C5. 이 모델은 왜 한국어를 못하나: 토크나이저 해부★★★★

SmolLM2의 실제 토크나이저(약 2MB)를 내려받아 같은 뜻의 영어·한국어 문장을 토큰으로 자른다. 한국어 한 글자가 토큰 몇 개가 되는지, 바이트 조각이 얼마나 많은지 센다. 그다음 SmolLM2의 채팅 템플릿으로 프롬프트 문자열을 만들어(10주차) 실제 모델에 들어가는 토큰 수를 센다. 처음 실행은 내려받기 때문에 10초를 넘을 수 있다. 그러면 한 번 더 실행한다(캐시됨).

6정리 & 과정을 마치며

  • 이미 학습된 LLM도 브라우저 안에서 추론할 수 있다. 데이터가 기기 밖으로 나가지 않고, 한 번 내려받으면 비용이 없고, 오프라인에서도 동작한다.
  • 모델 크기 = 파라미터 수 × 가중치당 바이트. 양자화는 이 바이트를 줄인다. 어휘가 큰 모델은 임베딩 표를 어떻게 저장하느냐가 크기를 좌우한다.
  • 작은 모델은 한국어·사실 지식·추론에서 금방 한계에 닿는다. 근거를 넣어 주면(RAG) 135M 모델도 “12시간”을 찾아내지만, 같은 답 안에서 “문서에 없다”고 말하는 모순도 섞는다. 근거는 필요조건이고, 근거를 제대로 읽는 능력은 모델 크기에 달려 있다.
  • 로컬과 API는 우열이 아니라 선택이다. 개인정보 · 비용 · 품질 · 속도 · 오프라인 조건으로 고른다.

studyRAG로 이어서 — 관찰 질문 3에서 135M짜리 모델도 근거 문장을 주자 “12시간”을 찾아냈다. 문제는 “어떤 문장을 넣어 줄 것인가”다. RAG 시스템 구축 과정에서 청킹 · 임베딩 검색 · 평가로 그 문장을 자동으로 찾는다. 5주차는 이번 주와 같은 Transformers.js로 임베딩 모델을 브라우저에서 돌린다.

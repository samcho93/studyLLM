한 번 묻기에서 천 번 돌리기로

11주차에는 LLM에게 질문 하나를 보내고 답 하나를 받았다. 실무에서는 문서 수백 개를 요약하고, 문의 수천 건을 분류하고, 공문에서 날짜와 금액을 뽑는다. 이때 LLM은 채팅 상대가 아니라 파이프라인의 한 단계다. 이번 주는 코퍼스 17문서를 한꺼번에 처리하는 일괄 처리기를 만들고, 출력이 “가끔” 깨지는 것을 코드로 잡아내고, 결과를 골드셋과 비교해 숫자로 평가한다.

1학습 목표

이번 주가 끝나면
  • 요약·분류·정보 추출을 프롬프트 템플릿 하나로 여러 문서에 적용하고, 출력 형식(길이, 라벨 집합, JSON 스키마)을 코드로 검사할 수 있다.
  • 작은 골드셋으로 정확도·혼동 행렬·필드 단위 정확 일치를 계산해 제로샷과 퓨샷 프롬프트를 숫자로 비교할 수 있다.
  • 동시 실행 제한·재시도·캐시를 갖춘 일괄 실행기를 만들고, 호출 수와 비용을 실행 전에 어림할 수 있다.

2왜 필요한가

11주차 플레이그라운드에서 “이 문서를 한 줄로 요약해 줘”를 보내면 대개 좋은 답이 온다. 그래서 문서 1,000개도 똑같이 하면 될 것 같다. 해 보면 다섯 가지 문제가 한꺼번에 터진다.

  1. 형식이 가끔 깨진다. “라벨만 답하라”고 해도 “분류 결과: 이론-LLM”이라고 답하고, JSON을 달라고 해도 코드 펜스(```json)나 “위 JSON은…” 같은 설명을 붙인다. 한 번이면 눈으로 고치지만, 1,000건 중 3%면 30건이 조용히 망가진다.
  2. 그럴듯하게 틀린다. 교과목 문서가 아닌 학과 소개에서 “학점: 3”을 뽑아낸다. 형식은 완벽하므로 파싱 검사로는 걸러지지 않는다.
  3. API가 거절한다. 짧은 시간에 요청을 몰아 보내면 429(요청 한도 초과)가 돌아온다. 재시도 없이 돌리면 일부 문서가 빈칸으로 남는다.
  4. 비용과 시간이 보이지 않는다. 문서 하나에 1원이 안 되더라도 퓨샷 예시를 붙이면 입력이 50% 늘고, 같은 문서를 두 번 보내면 두 번 낸다.
  5. 좋아졌는지 모른다. 프롬프트를 고친 뒤 “이번 게 더 나은 것 같다”는 느낌만 남는다. 정답을 아는 작은 평가 세트가 없으면 개선을 증명할 수 없다.
이번 주의 관점

LLM 호출은 함수 호출이 아니라 네트워크 너머 확률 모델의 호출이다. 실패는 예외가 아니라 일상이므로, 출력은 항상 검사하고, 호출은 항상 재시도·제한·캐시를 거치고, 결과는 항상 골드셋으로 잰다.

3개념

일괄 처리 파이프라인

문서 N개를 처리하는 코드는 다섯 단계로 나뉜다. LLM이 하는 일은 ③의 호출 한 번뿐이고, 나머지는 모두 우리가 짜는 평범한 코드다.

세 가지 작업과 출력 계약

작업마다 “출력이 어떤 모양이어야 하는가”를 먼저 정한다. 이것을 출력 계약이라 부르자. 계약이 정해져야 코드로 검사할 수 있다.

작업출력 계약코드로 하는 검사예시 응답에서 본 실패
요약N자 이내 평문 한두 문장글자 수, 서두 문장(“다음은…”), 핵심어 포함152자 요약(제한 100자), “24시간 개방”처럼 문서에 없는 내용
분류고정된 라벨 5개 중 하나라벨 집합에 있는지, 골드 라벨과 같은지“데이터베이스”(집합 밖), “분류 결과: 이론-LLM”(군더더기)
정보 추출필드 5개짜리 JSON 객체JSON.parse, 필드·타입 검사, 값 정규화코드 펜스, JSON 뒤 설명문, “3학점” 문자열, 없는 값 채우기

분류에서 라벨을 고정된 집합으로 주는 이유는 집계 때문이다. 라벨이 자유 문장이면 “RAG 이론”, “검색 이론”, “이론(RAG)”이 모두 다른 값이 되어 셀 수 없다. 추출에서는 스키마(필드 이름과 타입)가 같은 역할을 한다. 정규화(normalization)는 “3학점” → 3, “주 1회 3시간” → 3, “40%” → 40처럼 같은 뜻의 다른 표기를 하나로 맞추는 일이다. 정규화는 형식만 고칠 수 있다. 문서에 없는 값을 지어낸 환각은 정규화로 고칠 수 없다.

제로샷과 퓨샷

지시문만 주는 것을 제로샷(zero-shot), 입력과 정답 예시 몇 개를 함께 주는 것을 퓨샷(few-shot)이라 한다. 예시는 “라벨만 한 단어로” 같은 형식을 말보다 확실하게 보여 준다. 대신 매 호출마다 예시만큼 입력 토큰이 늘어난다. 이번 주 예시 응답으로 잰 값은 다음과 같다.

작업 (기본 템플릿)제로샷퓨샷입력 토큰 (추정)
분류 17문서 · 정확도12/17 (71%)16/17 (94%)5,670 → 8,458 (+49%)
추출 4문서 · 필드 일치 (엄격한 파싱)6/2019/201,446 → 2,174
요약 17문서 · 규칙 통과 (100자)13/1717/175,398 → 6,869

퓨샷으로도 남는 오류가 있다. “임베딩과 유사도”(RAG 교안)는 LLM 교안의 “임베딩”과 주제가 겹쳐 끝까지 이론-LLM으로 분류된다. 예시를 늘리기보다 라벨의 정의(“RAG 교안: 검색·청킹·평가 등 RAG 파이프라인을 다루는 문서”)를 템플릿에 적는 편이 낫다. 이런 판단은 혼동 행렬을 봐야 할 수 있다.

평가: 작은 골드셋

골드셋(gold set)은 사람이 정답을 달아 둔 작은 평가용 데이터다. 이번 주는 17문서마다 분류 정답, 요약 핵심어 세 개, 안내 문서 4개의 추출 정답을 assets/data/w13/gold.json에 만들어 두었다. 20~50개면 충분하다. 목적은 모델의 절대 실력이 아니라 프롬프트 A와 B 중 무엇이 나은가를 같은 잣대로 재는 것이다.

  • 정확도: 맞힌 문서 수 / 전체. 분류의 기본 지표다.
  • 혼동 행렬(confusion matrix): 행은 정답, 열은 예측. 대각선 밖의 칸이 “무엇을 무엇으로 착각하는가”를 보여 준다. 제로샷에서는 이론-RAG 6개 중 2개가 이론-LLM 칸에 들어간다.
  • 필드 단위 정확 일치: 추출은 문서 단위로 맞다/틀리다 하기엔 거칠다. 필드마다 정규화한 값이 정답과 같은지 센다. 정답이 null인데 값을 채웠으면 환각으로 따로 센다.
  • 요약은 정답 문장이 하나로 정해지지 않는다. 길이 제한 준수와 핵심어 포함률처럼 코드로 셀 수 있는 규칙부터 잰다.

파싱을 얼마나 관대하게 하느냐도 점수를 바꾼다. 추출 제로샷 응답 4개 중 JSON.parse를 통과하는 것은 2개뿐이지만, 코드 펜스와 뒤 설명문을 걷어 내면 4개 모두 파싱되고 필드 일치가 6/20에서 15/20으로 오른다. 남은 5개 오류 중 4개는 환각이다.

긴 문서: 맵-리듀스 요약

문서가 모델의 컨텍스트 창보다 길면 한 번에 넣을 수 없다. 이때 문서를 문단 단위 청크로 나눠 각각 요약하고(map), 부분 요약을 모아 다시 요약한다(reduce). 모은 것이 아직 길면 한 번 더 반복한다.

맵-리듀스는 호출 수가 청크 수만큼 늘고, 단계마다 정보가 조금씩 빠진다. C4의 최종 요약에는 첫 청크와 다섯 번째 청크의 첫 문장만 남는다. 청크를 문단 경계에서 자르는 이유는 RAG의 청킹과 같다. 문장 중간에서 자르면 두 청크 모두 그 문장을 제대로 요약하지 못한다.

예를 들어 기본 분류 템플릿으로 17문서를 돌리면 입력은 약 5,670토큰, 출력은 약 69토큰이다. 예시 단가(입력 100만 토큰당 1달러, 출력 5달러)로 약 0.006달러, 문서 1,000개로 환산하면 약 0.35달러다. 단가는 모델과 시기마다 다르므로 실제 요금표를 보고 고친다. 중요한 것은 금액보다 무엇이 비용을 키우는가다. 분류는 출력이 짧아 입력(문서 + 지시문 + 예시)이 비용의 대부분이다. 퓨샷 예시 5줄이 문서마다 반복된다는 점을 기억한다.

4실습

작업(요약·분류·정보 추출)을 고르고 프롬프트 템플릿을 고치면 선택한 문서 전체에 같은 템플릿이 채워져 나간다. 키가 없으면 예시 응답 모드로 동작한다. 예시 응답은 기본 템플릿에 대해 미리 작성해 둔 수업용 응답이며, 실제 LLM에서 자주 보는 실패를 일부러 넣어 두었다. 결과는 오른쪽 실행 결과 창에 나온다(휴대폰에서는 위젯 바로 아래). 표의 행을 누르면 그 문서에 실제로 나간 프롬프트와 원문 응답, 판정 이유가 나온다.

관찰 질문

  1. 처음 화면(분류 · 제로샷 · 엄격한 파싱)의 정확도와 “형식 유효” 값을 적는다. 혼동 행렬에서 대각선 밖에 있는 칸은 어느 것인가? ✗ 열(라벨 무효)에 들어간 문서의 원문 응답은 무엇인가?
  2. 관대한 파싱을 켠다. 정확도가 어떻게 변하는가? 이때 “LLM 호출” 수가 늘지 않는 이유는 무엇인가? “데이터베이스”는 왜 여전히 복구되지 않는가?
  3. 퓨샷 예시를 켠다. 정확도와 토큰(입력) 값이 각각 얼마로 바뀌는가? 남은 오류 한 건은 어떤 문서이고, 왜 헷갈릴 만한가?
  4. 작업을 정보 추출로 바꾼다. 엄격한 파싱에서 형식 유효는 몇 개인가? 관대한 파싱을 켠 뒤 “학과 소개” 행을 눌러 판정 이유를 읽는다. 파싱이 성공했는데도 ✗인 이유와, 어떤 필드가 환각인지 적는다.
  5. 작업을 요약으로 바꾸고 길이 제한을 100자 → 70자로 줄인다. 길이 준수는 몇 개가 되는가? “N자 이내”라고 프롬프트에 적었는데도 코드로 길이를 검사해야 하는 이유를 한 문장으로 쓴다.
  6. 캐시 사용을 끄고 동시 실행 수를 1과 4로 바꿔 가며 ▶ 일괄 실행을 누른다. 소요 시간은 어떻게 변하는가? “재시도” 3회는 어느 문서에서 생겼나(시도 열의 ↻)? 캐시를 다시 켜고 같은 설정으로 두 번 실행하면 호출 수는?
  7. 분류에서 캐시를 끄고 온도를 0.8로 올린 뒤 ▶ 일괄 실행을 여러 번 누른다. 매번 바뀌는 문서는 어느 것인가? 온도 0으로 돌리면 어떤가? 온도 0.8에서 캐시를 켜면 어떤 문제가 생기는가?
  8. (API 키가 있으면) 실제 LLM 모드에서 분류 17문서를 돌린다. 실행 전 추정 비용과 실행 후 비용을 비교하고, 예시 응답과 다르게 나온 문서를 찾는다.

5Challenge

난이도 순서다. 코드 상자는 직접 고칠 수 있고, ▶ 실행(또는 Ctrl+Enter)을 누르면 결과가 오른쪽 실행 결과 창에 나온다. 모든 Challenge는 API 키 없이 예시 응답(/assets/data/w13/*.json)과 모의 LLM 함수로 동작한다. 코드는 워커에서 돌아가므로 10초가 넘으면 자동으로 멈춘다.

C1. 템플릿 채우기와 길이 검사★

function fnv1a(str) {
  let h = 0x811c9dc5;
  for (let i = 0; i < str.length; i++) h = Math.imul(h ^ str.charCodeAt(i), 0x01000193) >>> 0;
  return h.toString(16).padStart(8, '0');
}
const stats = { calls: 0, inFlight: 0, maxInFlight: 0 };
const failedOnce = new Set();
async function mockLLM(prompt) {
  stats.calls++;
  stats.inFlight++;
  stats.maxInFlight = Math.max(stats.maxInFlight, stats.inFlight);
  try {
    await sleep(25);
    const h = fnv1a(prompt);
    if (parseInt(h, 16) % 5 === 0 && !failedOnce.has(h)) {
      failedOnce.add(h);
      const e = new Error('429 Too Many Requests');
      e.status = 429;
      throw e;
    }
    const doc = prompt.split('"""\n')[1]?.split('\n"""')[0];
    return answer.get(doc) ?? '모름';
  } finally {
    stats.inFlight--;
  }
}

6정리 & 다음 주 예고

  • LLM 일괄 처리는 템플릿 채우기 → 호출 → 파싱·검증 → 평가로 이어지는 파이프라인이다. LLM은 그중 한 단계일 뿐이다.
  • 작업마다 출력 계약(길이, 고정 라벨 집합, JSON 스키마)을 정하고 코드로 검사한다. 정규화는 표기를 고치지만 환각은 고치지 못한다.
  • 작은 골드셋으로 정확도·혼동 행렬·필드 단위 일치를 재면 제로샷과 퓨샷, 엄격한 파싱과 관대한 파싱을 숫자로 비교할 수 있다.
  • 호출은 동시 실행 제한, 지수 백오프 재시도, 해시 캐시로 감싸고, 재현이 필요하면 온도 0을 쓴다. 비용은 실행 전에 토큰으로 어림한다.
  • 컨텍스트보다 긴 문서는 문단 단위로 나눠 맵-리듀스로 요약한다. 호출이 늘고 정보가 조금씩 빠진다는 대가가 있다.

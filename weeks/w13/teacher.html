응용 실습 주차다. 정규 12주의 개념(프롬프트, 온도, 토큰, JSON 출력)을 “많이, 안정적으로, 재 가며” 쓰는 법이 주제다. API 키가 없어도 모든 활동이 예시 응답으로 돌아간다는 점을 먼저 알린다. 키를 쓰는 학생에게는 키를 화면 공유하지 말라고 짚는다.

한 번 잘 되면, 천 번도 잘 될까?

1,000건 × 3% 형식 오류 = 조용히 망가진 30건

  • “라벨만 답하라” → 분류 결과: 이론-LLM
  • “JSON만” → ```json … ``` + “위 JSON은…”
  • 학과 소개에서 학점: 3을 지어낸다 (형식은 완벽)
  • 몰아 보내면 429 · 두 번 보내면 두 번 낸다

발문: “11주차 플레이그라운드에서 요약이 잘 됐다. 학과 공지 1,000개를 요약하라는 일을 받으면 무엇부터 할까?” → 대부분 반복문 하나를 떠올린다. 그 반복문에서 무엇이 터지는지를 오늘 하나씩 본다.

예시는 모두 오늘 쓰는 예시 응답에 실제로 들어 있는 실패다. 실제 LLM에서도 흔히 본다.

오늘 할 수 있게 되는 것

  1. 템플릿 하나로 요약·분류·추출을 여러 문서에 적용하고 출력 계약을 코드로 검사한다
  2. 작은 골드셋으로 정확도·혼동 행렬·필드 일치를 재서 프롬프트를 숫자로 비교한다
  3. 동시 실행 제한 · 재시도 · 캐시가 있는 일괄 실행기를 만들고 비용을 어림한다

목표 2가 오늘의 중심이다. “느낌”이 아니라 “12/17 → 16/17”로 말하는 습관을 만든다. RAG 9주차 평가로 그대로 이어진다.

LLM은 파이프라인의 한 단계일 뿐

① 템플릿문서마다 채우기{{document}} · {{labels}}
② 호출 풀LLM 호출동시 ≤ k · 재시도 · 캐시
③ 검증파싱 · 스키마 · 정규화✓ / ✗ / ⚠
④ 평가골드셋 비교정확도 · 혼동 행렬

LLM이 하는 일은 ②뿐, 나머지는 평범한 코드다

학생 문서의 그림과 같은 구조다. ②는 느리고 비싸고 가끔 실패한다 → 감싸는 코드가 필요하다. ③④가 없으면 “잘 되는 것 같다”로 끝난다.

①의 입력(문서 텍스트)을 어디서 얻는지는 RAG 3주차(문서 로딩 & 파싱)에서 다룬다고 짚는다.

숫자는 위젯이 쓰는 예시 응답과 같은 추정 방식(한국어 1.5자 ≈ 1토큰)으로 계산한 값이다.

퓨샷 예시는 코퍼스 밖 문장으로 만들었다(도서관 규정 등). 평가 문서를 예시로 쓰면 점수가 부풀려진다 — 데이터 누수.

JSON 추출은 세 단계로 검사한다

LLM 원문 응답

```json
{"과목명": "LLM 원리와 활용",
 "학점": "3학점",
 "주당_수업시간": "주 1회 3시간", …}
```

검사

  1. 파싱: parse → 실패하면 펜스·설명문 걷어 내기
  2. 검증: 필드 이름·개수·타입, 성적 합 100
  3. 정규화: “3학점” → 3, “40%” → 40

parse만: 2/4 파싱 · 필드 6/20
세 단계: 4/4 파싱 · 필드 15/20 · 환각 4

관대한 파싱은 양날의 칼이다. 복구한 건수를 반드시 따로 센다(위젯은 “관대한 파싱” 판정 이유로 표시). 복구율이 높으면 프롬프트나 공급자의 JSON 모드를 고친다.

공급자의 구조화 출력(JSON 스키마 강제) 기능을 쓰면 1·2단계 실패가 크게 준다. 그래도 환각(3단계 뒤 골드 비교에서만 보임)은 남는다.

“RAG 시스템 구축 교과목 안내”가 RAG로 분류된 칸이 흥미롭다. 문서 주제와 문서 종류가 다르다. 라벨 정의가 모호하면 모델도 사람도 헷갈린다 → 라벨 정의를 템플릿에 적는다.

골드셋은 20~50개면 충분하다. 목적은 모델의 절대 점수가 아니라 A/B 비교다. 골드셋 자체의 오류도 가끔 발견된다 — 두 사람이 따로 라벨을 달아 비교하면 좋다.

긴 문서: 맵-리듀스 요약

2,640자 ──문단 경계──▶ 청크 8개 (각 ≤ 400자)
   map ①  청크마다 요약 → 합 698자  (아직 > 400)
   map ②  다시 청크 2개 → 합 138자
   reduce 최종 요약 1회
   호출 = 8 + 2 + 1 = 11회
  • 호출 수는 청크 수만큼 늘고, 단계마다 정보가 빠진다
  • 문장 중간에서 자르지 않는다 — RAG 청킹과 같은 이유

Challenge C4의 실제 실행 결과다. 모의 요약기는 “문단마다 첫 문장”을 고르는 추출 요약이다. 최종 요약에는 RAG 입문(첫 청크)과 임베딩(다섯째 청크)의 첫 문장만 남는다 → 청킹·벡터DB·평가 내용이 사라진다.

실제 LLM은 더 잘 합치지만 같은 경향(앞쪽 편향, 세부 누락)이 있다. 대안: 요약 대신 “문서별 핵심 사실 목록”을 뽑아 합치는 방법.

호출을 감싸는 다섯 가지

문제대책
몰아 보내면 429동시 실행 제한 — 작업자 k개가 대기열에서 하나씩
일시적 실패재시도 + 지수 백오프 150 → 300 → 600ms (401은 재시도 안 함)
같은 입력 반복캐시 — 키 = hash(모델 · 온도 · 프롬프트)
매번 다른 결과온도 0 + 결과 저장
비용 모름실행 전 어림 — 토큰 ≈ 글자 / 1.5

분류 17문서 ≈ 입력 5,670토큰 → 예시 단가($1/$5)로 $0.006 · 1,000문서 ≈ $0.35

단가는 예시다. 수업 당일 공급자 요금표로 바꿔 보여 준다(위젯 “비용 설정”에서 수정).

캐시 키에 온도·모델을 넣는 이유: 다른 모델의 답을 재사용하면 안 된다. 온도 > 0에서 캐시를 켜면 첫 무작위 결과가 고정된다 — 위젯이 이 경우 경고를 띄운다.

온도 0도 완전히 결정적이지 않다(병렬 연산 순서, 공급자 쪽 배치). “재현성 = 결과를 저장해 두는 것”이라고 정리한다.

재시도와 캐시, 코드 30줄

const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
let calls = 0;
async function flakyLLM(prompt) { // 처음 두 번은 429를 낸다
  calls++;
  if (calls <= 2) {
    const e = new Error('429 Too Many Requests');
    e.status = 429;
    throw e;
  }
  return `요약: ${prompt.slice(0, 12)}…`;
}
async function withRetry(fn, retries = 3, base = 100) {
  for (let attempt = 0; ; attempt++) {
    try {
      return await fn();
    } catch (e) {
      if (e.status !== 429 || attempt >= retries) throw e;
      const wait = base * 2 ** attempt; // 100 → 200 → 400ms
      console.log(`시도 ${attempt + 1} 실패 (${e.message}) → ${wait}ms 뒤 재시도`);
      await sleep(wait);
    }
  }
}
const cache = new Map();
async function cachedCall(prompt) {
  if (cache.has(prompt)) return { text: cache.get(prompt), cached: true };
  const text = await withRetry(() => flakyLLM(prompt));
  cache.set(prompt, text);
  return { text, cached: false };
}
const doc = '실습실은 평일 오후 9시까지 개방된다.';
console.log(await cachedCall(doc));
console.log(await cachedCall(doc)); // 같은 프롬프트 → 캐시
console.log('실제 호출 수:', calls);

실행 결과: “시도 1 실패 → 100ms 뒤 재시도”, “시도 2 실패 → 200ms 뒤 재시도”, 첫 호출 cached: false, 두 번째 cached: true, 실제 호출 수 3.

e.status !== 429 조건을 지우고 “모든 오류를 재시도”하면 무엇이 문제인가? → 키 오류(401)나 잘못된 요청(400)도 세 번 더 보내 시간만 버린다.

정리

  • 일괄 처리 = 템플릿 → 호출 → 검증 → 평가, LLM은 한 단계
  • 출력 계약(길이 · 라벨 집합 · 스키마)을 정하고 코드로 검사한다. 정규화 ≠ 환각 수정
  • 골드셋으로 제로샷/퓨샷, 엄격/관대한 파싱을 숫자로 비교한다
  • 동시 제한 · 백오프 재시도 · 해시 캐시 · 온도 0 · 비용 어림

function fill(template, vars) {
  const missing = [];

}

function chunkByParagraph(text, maxChars) {

}

async function runBatch(prompts, { concurrency = 1, retries = 3, cache = null } = {}) {
  const results = new Array(prompts.length);
  let retried = 0;
  let hits = 0;
  async function withRetry(prompt) {
    for (let attempt = 0; ; attempt++) {
      try {
        return await mockLLM(prompt);
      } catch (e) {
        if (e.status !== 429 || attempt >= retries) throw e;
        retried++;
        await sleep(20 * 2 ** attempt);
      }
    }
  }
  let next = 0;
  async function lane() {
    while (next < prompts.length) {
      const i = next++;
      const key = fnv1a(prompts[i]);
      let p = cache?.get(key);
      if (p) hits++;
      else {
        p = withRetry(prompts[i]);
        cache?.set(key, p); // store the Promise: duplicates still in flight share it
      }
      try {
        results[i] = await p;
      } catch (e) {
        cache?.delete(key); // never cache failures
        results[i] = 'ERROR ' + e.message;
      }
    }
  }
  await Promise.all(Array.from({ length: concurrency }, lane));
  return { results, retried, hits };
}
